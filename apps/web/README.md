# @canvas/web — фронтенд

Редактор канваса на React 19, TypeScript и React Flow (`@xyflow/react`), собран Vite. Workspace называется `@canvas/web`; все команды выполняются из корня репозитория (npm workspaces), зависимости зафиксированы корневым `package-lock.json` (`npm ci`).

[Задание](../../docs/ASSIGNMENT.md) · [Работа с API](../../docs/INTEGRATION.md) · [Критерии оценки](../../docs/EVALUATION.md)

## Запуск и сборка

```sh
npm ci             # установка зависимостей всего воркспейса (из корня)
npm run dev        # терминал 1: API на 127.0.0.1:4001
npm run dev:web    # терминал 2: Vite-дев-сервер, http://localhost:5173
```

Продакшен-сборка и предпросмотр:

```sh
npm run build:web
npm run preview -w @canvas/web
```

Адрес API задаётся переменной `VITE_API_URL` (см. `.env.example`), по умолчанию `http://127.0.0.1:4001`.

При первом входе приложение создаёт пространство (форма с одним полем), сохраняет его id в `localStorage` и открывает при следующих заходах. Если пространство удалено на сервере (404), форма показывается снова.

## Устройство

```text
apps/web/src/
  api/            транспорт: client, errors, endpoints, poll
  graph/          модель графа, правила связей, операции над массивами нод
  sync/           GraphSynchronizer: debounce-очередь сохранения графа
  generation/     GenerationManager: запуск генераций и опрос статуса
  editor/         контекст редактора и хук, связывающий движки с React Flow
  components/     экраны и ноды
```

**Транспорт (api/).** Все запросы идут через один `apiRequest`: базовый адрес из одного места, общие заголовки, проверка статуса по списку ожидаемых, разбор пустого тела и `{"error":{code,message}}`. Сетевые, HTTP- и ошибки разбора нормализуются в `ApiError` с русским сообщением в единственном месте (`errors.ts`). `endpoints.ts` описывает только особенности каждой операции (метод, путь, тело, `If-Match`, `Idempotency-Key`). Ожидание и отмена переиспользуются универсальным `pollUntilSettled`.

**Сохранение графа (sync/).** `GraphSynchronizer` получает каждую правку, сбрасывает таймер debounce 500 мс и держит один PUT «в полёте» (single-flight): новые правки копятся в черновике и отправляются после завершения текущего запроса. Отправка идёт с `If-Match` на последний ETag. Ответ 412 переводит состояние в «конфликт»: локальный черновик сохраняется, пользователь может перечитать серверную версию. Незавершённая генерация не запускается, пока черновик не сохранён (см. ниже).

**Генерация (generation/).** По нажатию кнопки менеджер сначала досылает несохранённые правки (`flush` синхронизатора), берёт свежий ETag, затем отправляет `POST` с новым `Idempotency-Key`. Пока задание не завершено, кнопка заблокирована (и сервер отвечает 409 на повторный POST). Статус опрашивается с интервалом из `Retry-After`. Ошибка сети при старте повторяется тем же ключом и телом; явный «Повторить с новым ключом» после сбоя сценария запускает новую попытку. После перезагрузки страницы список генераций восстанавливает незавершённые попытки и результаты. Результат подставляется только в ноду, зафиксированную в снапшоте попытки, и не перезаписывает более новые попытки.

**Правила и данные (graph/).** Разрешённые связи (`текст → генератор`, `генератор → результат`, один вход, один результат у генератора) проверяются одной функцией `canConnect` по индексу графа. Она используется и для интерактивной валидации в React Flow, и при добавлении связи. `toApiGraph` собирает тело PUT whitelist-проходом: без служебных полей React Flow, позиции зажимаются в ±10000, zoom — в 0.1–4.

### Горячий участок: валидация связей во время протягивания

`isValidConnection` вызывается React Flow на каждое движение указателя при протягивании связи — десятки раз в секунду. Строить индекс графа при каждом вызове значило бы «индекс ради каждого обращения»: два прохода и новая `Map` + два `Set` на каждое движение. Индекс строится один раз на версию графа (`useMemo` по `nodes`/`edges`) и переиспользуется: проверка одной связи — два `Map.get` и до двух `Set.has`, без аллокаций. Сама пересборка индекса (два прохода, ≤20 нод и ≤20 связей) происходит только при структурной правке, а не на кадр протягивания.

Соседние пути по той же логике: `toApiGraph` — один проход на коллекцию в предвыделенные плотные массивы; `replaceNodeData` заменяет ссылку только изменённой ноды, остальные ссылки сохраняются, поэтому React Flow не перерисовывает нетронутые ноды; «грязность» черновика определяется сравнением ссылок, без глубоких сравнений; правки из кадров перетаскивания схлопываются debounce в один PUT.

## Проверенные сценарии

Логика транспорта, сохранения и генераций проверялась скриптами против живого API (62 проверки: транспорт и разбор ошибок; debounce, очередь PUT, single-flight, 412-конфликт; идемпотентный старт, опрос, 409, восстановление после перезагрузки, отмена). Сценарии интерфейса проверены вручную в браузере:

1. Создание пространства, переоткрытие после перезагрузки; 404 → форма создания.
2. Добавление трёх типов нод, перетаскивание, ввод текста (нода не тянется), связи только разрешённых типов; лишние входы и второй результат запрещены; удаление нод и связей (кнопка и Delete).
3. Статусы сохранения: «есть несохранённые правки» → «сохраняем» → «сохранено»; одиночная правка тоже сохраняется; ошибки сети видны и повторяются.
4. Генерация сразу после правки: сначала досылается сохранение, затем запуск; успех — картинка в связанной ноде результата; сценарий «сбой» — ошибка и повтор с новым ключом; двойное нажатие не создаёт дублей.
5. Перезагрузка посреди генерации: попытка отслеживается и завершается в UI.
6. Конфликт: правка графа через Swagger → 412 → баннер, черновик цел, перечитывание с сервера.

## Известные недоработки

- Одно пространство на браузер (id в `localStorage`), экрана со списком пространств нет.
- Выбор сценария генерации живёт в памяти страницы и после перезагрузки сбрасывается на «успех».
- Новые ноды появляются в центре видимой области со случайным смещением ±20% — редкие частичные перекрытия возможны.
- История генераций растёт без ограничений (у API нет удаления — так задумано); при открытии читается весь список.
- Автоматических тестов нет: логика покрыта сценарными скриптами и ручной проверкой (см. выше).
- В dev-режиме React StrictMode монтирует экран дважды — видны повторные запросы загрузки; в продакшен-сборке этого нет.
