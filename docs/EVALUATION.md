# Как оцениваем решение

В первую очередь смотрим, насколько хорошо обобщён код. Повторяющиеся операции должны иметь одну реализацию: запросы, разбор ответов, ошибки, работа с данными и одинаковое поведение интерфейса. Чем меньше мест приходится менять ради одного общего правила, тем лучше.

За каждое задание можно получить 100 баллов: **DRY и обобщение — 40, производительность — 10, основной сценарий — 20, устойчивость — 20, интерфейс — 5, запуск и описание — 5**.

У каждого пункта три оценки: **5** — выполнен целиком, **2** — выполнен частично, **0** — не выполнен. При снижении оценки записываем конкретный пример и указываем, какая часть работает. Если проверке помешала наша среда, оставляем пункт без оценки до повторной проверки.

## DRY и обобщение — 40 баллов

| Пункт | Что проверим — по 5 баллов                                                                                                                                                                                         |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| D1    | Все запросы к API проходят через общий механизм отправки. В компонентах нет собственных вариантов fetch с одинаковыми обязанностями.                                                                               |
| D2    | Адрес API, общие заголовки и подготовка тела запроса задаются в одном месте. Для нового запроса достаточно описать его особенности.                                                                                |
| D3    | Проверка HTTP-статуса, пустого ответа и разбор тела выполняются общим кодом. Компоненты получают данные с понятными типами, без повторных проверок сырого Response и формата общего ответа.                        |
| D4    | Сетевые, HTTP-ошибки и ошибки разбора приводятся к единому виду в одном месте. Каждый вызов не повторяет одинаковый catch, выбор сообщения и разбор полей ошибки.                                                  |
| D5    | Повторяющаяся логика ожидания, опроса, отмены и повторов переиспользуется. Особенности конкретной операции задаются явно; одинаковые циклы и обработчики не скопированы по страницам или нодам.                    |
| D6    | Одинаковые правила проверки данных, преобразования и вычисления имеют одну реализацию. Компоненты не содержат расходящихся копий одного правила.                                                                   |
| D7    | Повторяющееся поведение полей, кнопок и состояний интерфейса обобщено. Исправление общего поведения не требует обходить все места его использования.                                                               |
| D8    | Подготовку запроса, отправку, разбор ответа и обработку ошибки можно менять независимо. Изменение общего правила не требует править его потребителей. По типам и параметрам понятно, как пользоваться общим кодом. |

**Решение не проходит отбор, если одинаковые проверки HTTP-ответа или разбор однотипных ошибок повторяются в компонентах.** Обёртки, которая только возвращает `fetch(...)`, недостаточно, если `response.ok`, `response.json()` и обработка ошибок снова написаны в каждом месте вызова.

Компонент может показать уже разобранную ошибку, связать её с полем или предложить действие. Проверка состояния заказа или генерации тоже нужна: например, `failed` в данных успешного HTTP-ответа — состояние операции. Это отличается от повторного разбора транспорта.

Обобщайте всё, что действительно повторяется. Название подхода, число файлов и выбор библиотеки не дают баллов сами по себе. Если операция встречается один раз, отдельная абстракция только ради оценки не нужна. Разные правила не нужно прятать за растущим набором флагов. Общий пакет между двумя репозиториями необязателен: оцениваем устройство каждого решения.

## Производительность — 10 баллов

| Пункт | Что проверим — по 5 баллов                                                                                                                                                                                                                                                                   |
| ----- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P1    | В часто выполняемой обработке данных нет лишних проходов, промежуточных массивов, копирования растущего результата или повторного линейного поиска внутри обхода. Выбран способ с меньшей стоимостью для той же задачи; индекс или кэш не строится заново ради каждого обращения.            |
| P2    | Изменение одного значения не запускает без необходимости пересчёт всех данных, пересоздание всех объектов и повторные запросы. Обновления сохраняют неизменившиеся ссылки, где это позволяет состояние. В коллекциях не создаются ненужные дырки и не смешиваются типы значений без причины. |

Например, `.map().filter()` создаёт промежуточный массив и выполняет второй проход. Если тот же результат с тем же поведением можно получить за один проход без этого массива, в часто вызываемом коде ожидаем такой вариант. Это особенно заметно при обработке больших коллекций и частых изменениях канваса. Необоснованно более дорогой вариант снижает P1. Смотрим на операции и выделение памяти: сам по себе `.reduce()` не даёт преимущества, а копирование растущего аккумулятора на каждом шаге может привести к квадратичной сложности.

При повторном поиске по идентификаторам учитывайте стоимость обходов и возможность переиспользовать `Map` или `Set`. Если нужен только первый подходящий элемент, нет причины строить все результаты. Копия для корректного обновления состояния React необходима; лишними считаются копии и пересчёты, от которых можно отказаться без изменения поведения.

Для массивов важны и форма данных, и особенности движка. Например, V8 различает плотные массивы и массивы с дырками, а также способы хранения чисел и обычных элементов. Дырка после `delete items[i]` отличается от элемента со значением `undefined`. Учитывайте это в часто выполняемом коде; подробности — в [документации V8](https://v8.dev/blog/elements-kinds) и [спецификации массивов](https://tc39.es/ecma262/multipage/indexed-collections.html).

В README достаточно разобрать один реальный участок обработки данных: как часто он вызывается, сколько делает проходов и что создаёт в памяти. Отдельный отчёт с замерами не нужен. Если преимущество зависит от движка или неочевидно, его проверяют профилированием, а не названием метода. Читаемость и корректность должны сохраняться.

## Основной сценарий — 20 баллов

| Пункт | Что проверим — по 5 баллов                                                                                                                                                       |
| ----- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A1    | Пространство создаётся и открывается через API. Добавляются три типа нод с уникальными идентификаторами; перемещение и редактирование текста сразу видны.                        |
| A2    | Связи создаются между портами перетаскиванием. Несовместимые типы и лишние входы или выходы запрещены; нода удаляется вместе со связями, сервер принимает оставшийся граф.       |
| A3    | Ноды, связи и положение канваса сохраняются через PUT с актуальным If-Match. Нажатие генерации сразу после правки дожидается сохранения последнего графа и запускает его версию. |
| A4    | После ожидания сервер подтверждает успех, картинка с API появляется в связанной ноде результата.                                                                                 |

## Устойчивость — 20 баллов

| Пункт | Что проверим — по 5 баллов                                                                                                                                                                                                                                    |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| B1    | Быстрые правки дают одно сохранение после паузы 500 мс; одиночная правка тоже сохраняется. При медленном ответе PUT одного графа выполняются последовательно, новые правки не теряются. Допускается небольшая задержка таймера браузера.                      |
| B2    | При 412 локальный черновик остаётся доступен, виден конфликт и можно явно перечитать серверный граф. Сбой сохранения не запускает генерацию и не стирает правки.                                                                                              |
| B3    | Перезагрузка восстанавливает граф и результаты; незавершённая генерация отслеживается. Тестовый отказ допускает новый запуск. Двойное нажатие и повтор после потери ответа не создают дублей: повтор сохраняет тело и ключ, новый запуск получает новый ключ. |
| B4    | Опрос прекращается после завершения или закрытия пространства. Результат удалённой или переподключённой цепочки не подставляется в другую ноду или поверх более новой попытки.                                                                                |

## Интерфейс — 5 баллов

| Пункт | Что проверим — 5 баллов                                                                                                                                                                                                                                                                                                             |
| ----- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| C1    | Сохранение, ожидание, ошибка и успех различимы; видно, что ещё не сохранено. Подписи и порты помогают собрать цепочку, ввод текста не перетаскивает ноду. При ширине 1280 пикселей основные элементы доступны, поля и кнопки подписаны и работают с клавиатуры. Ошибки объясняют следующее действие. Мобильную версию не оцениваем. |

## Запуск и описание — 5 баллов

| Пункт | Что проверим — 5 баллов                                                                                                                                                                                                        |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| E1    | Из свежего клона по README можно установить зависимости, запустить API и фронтенд, собрать приложение. Есть файл фиксации зависимостей, описание общего кода и обработки данных, проверенные сценарии и известные недоработки. |

Проверки можно описать вручную или автоматизировать. Баллы даём за подтверждённое поведение; количество тестов, коммитов или строк кода преимуществом не будет. Дополнительные функции и деплой не добавляют баллов. Можно пользоваться любыми инструментами, включая библиотеки и нейросети; на встрече обсудим код и небольшое изменение в нём.

## Кого пригласим

Для отбора нужны оба решения. За каждое можно получить до 100 баллов, суммарно — до 200.

В первую группу попадают кандидаты, у которых **в каждом задании**:

- от 75 баллов всего;
- D ≥ 30 за обобщение, A ≥ 15 за основной сценарий и B ≥ 10 за устойчивость;
- D1, D3 и D4 выполнены целиком — по 5 баллов;
- основной путь до результата проходит целиком, нет ложного успеха и тихой потери данных.

В этой группе **сначала сравниваем сумму D по двум заданиям, затем сумму P, затем общий результат из 200 баллов**. Так преимущество получает работающий код с лучшим переиспользованием и меньшей стоимостью повторяющихся операций. Если все три значения равны, проводим повторную проверку или приглашаем обоих кандидатов.

Баллы не гарантируют приглашение. Работы ниже порога разбираем по конкретным пробелам; повторяющийся разбор HTTP-ответов и ошибок в компонентах остаётся причиной не пройти отбор независимо от суммы. Решения смотрим раз в три дня. Использованные инструменты на приоритет не влияют.
